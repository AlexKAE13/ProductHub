## 0. Как работать с этим документом

ТЗ разбито на этапы (раздел 9). Каждый этап - отдельная сессия разработки с понятным результатом. Порядок такой:

1. Взять следующий этап из раздела 9 и прочитать связанные с ним разделы ТЗ.
2. Сделать этап целиком, не забегая вперед. Заготовки под будущие этапы допустимы только там, где ТЗ прямо об этом говорит (например, поля под 1С).
3. Проверить критерии готовности этапа, прогнать тесты, обновить STATUS.md.
4. Показать результат, получить подтверждение и только потом переходить к следующему этапу.

Если ТЗ противоречит само себе или чего-то не хватает для решения, нужно спросить, а не додумывать. Мелкие технические решения внутри этапа разработчик принимает сам и записывает в STATUS.md (раздел "Решения").

## 1. Что строим и зачем

Product HUB - внутреннее веб-приложение Eltex. В нем по каждому артикулу (SKU) собрано все, что нужно знать о продукте: характеристики, статус жизненного цикла, прошивки, даташиты, презентации, battle cards, кейсы, цена и наличие, вопросы и ответы. Плюс база артефактов отдела: материалы, которые не привязаны к одному SKU (презентации направления, шаблоны КП, гайды, отчеты).

Проблема, которую решаем: информация о продукте разбросана по Confluence, сетевым дискам, почте и головам людей. Менеджер не может быстро ответить клиенту, версии в даташите, презентации и на сайте расходятся, RU и EN живут отдельно, новый сотрудник неделями собирает информацию.

Главный принцип - SSoT (единый источник правды). У каждого факта и каждого файла ровно одно мастер-место и один ответственный. Карточка SKU не копирует материалы, а показывает их по связям (тегам). Обновили файл в одном месте - он обновился везде.

Второй принцип - скорость. Менеджер должен найти ответ за минуту. Отсюда мгновенный поиск и легкие страницы (раздел 8).

Третий принцип - база живет за счет процессов, а не памяти людей. События (новая прошивка, новый вопрос, устаревший материал) автоматически создают задачи ответственным.

### 1.1. Масштаб

- Около 300 SKU в компании, на старте линейки Wi-Fi и PON (около 80 SKU в реестре ЖЦ Wi-Fi).
- Несколько тысяч материалов.
- 50-200 пользователей, одновременно до 50.

### 1.2. Что точно не входит в первую версию

Интеграция с 1С, внешний (партнерский) контур, ИИ-ассистент, вход через корпоративные учетные записи. Под все это закладывается структура, но реализуется позже (раздел 9, этапы 7+).

## 2. Роли

| Роль | Код | Что может |
|---|---|---|
| Продакт-менеджер | PRODUCT | Все: создание и правка SKU, материалов, прошивок, кейсов, тегов; ответы на вопросы, принятие правок, управление задачами |
| Сервисный центр | SERVICE_CENTER | Правка технических блоков карточки и прошивок, загрузка материалов, ответы на технические вопросы |
| Менеджер по продажам | SALES | Чтение, скачивание, поиск, вопросы и предложения правок |
| R&D, техподдержка | RND | Чтение, вопросы и предложения правок, публикация прошивок |
| Руководитель | HEAD | Чтение, дашборд |
| Администратор | ADMIN | Пользователи, роли, справочники, импорт |
| Партнер (позже) | PARTNER | Только внешний контур. В v0 не реализуется, но код проверки контура пишется сразу |

Правила:
- Прямую правку карточек делают только PRODUCT и SERVICE_CENTER (последний - только технические блоки). Остальные вносят вклад через "Вопросы и правки".
- Владелец SKU - конкретный продакт. Задачи по SKU по умолчанию падают ему.
- У пользователя может быть несколько ролей.
- В v0 нет настоящей авторизации. Есть набор тестовых пользователей и переключатель "войти как" в шапке (только в профиле dev). Весь доступ при этом проверяется через Spring Security по ролям, чтобы потом подключить AD/LDAP без переделки.

## 3. Стек и архитектура

| Слой | Технология |
|---|---|
| Язык | Java 21 LTS (допустим 25 LTS) |
| Фреймворк | Spring Boot последней стабильной версии, сборка Maven с wrapper (`./mvnw`) |
| Веб | Spring MVC + Thymeleaf, интерактив через HTMX. JS-фреймворков нет |
| JS-библиотеки | htmx, SortableJS (канбан). Подключаются как локальные файлы в `static/`, без CDN, сборки через Node нет |
| CSS | Свой небольшой CSS-файл. Простой нейтральный стиль: белый фон, серая шкала, один акцентный цвет. Без тяжелых UI-китов |
| БД | H2 в файловом режиме локально (профиль dev), PostgreSQL в компании (профиль prod). Переключение только через настройки |
| Миграции | Flyway. SQL пишется так, чтобы работал и в H2 (режим совместимости PostgreSQL), и в PostgreSQL |
| Доступ к данным | Spring Data JPA |
| Поиск | Hibernate Search с бэкендом Lucene (индекс на диске). Одинаково работает с H2 и PostgreSQL |
| Безопасность | Spring Security: роли, CSRF, проверка прав на уровне сервисов |
| Файлы | Хранение на диске в папке `data/files` через интерфейс `FileStorage`. Позже можно заменить на S3/MinIO, не меняя остальной код |
| Чтение Excel | Apache POI (импорт реестров) |
| Планировщик | Spring `@Scheduled` (ежедневные проверки устаревания) |
| Тесты | JUnit 5, Spring Boot Test, Testcontainers для PostgreSQL на этапе 7 |

### 3.1. Структура кода

Код раскладывается по модулям (package by feature), а не по слоям:

```
ru.eltex.producthub
  common/      общие вещи: аудит, ошибки, утилиты, замер времени
  security/    пользователи, роли, переключатель dev-пользователя
  tag/         теги и справочник тегов
  sku/         SKU, линейки, характеристики, коммерческий блок
  artifact/    база артефактов (материалы), типы, версии, файлы
  firmware/    прошивки
  casestudy/   кейсы
  qa/          вопросы и правки, FAQ
  task/        задачи, канбан, триггеры событий
  search/      мгновенный поиск, журнал запросов
  dashboard/   дашборд
  importer/    импорт Excel и папок с файлами
  web/         общий layout, главная страница
```

Внутри модуля: `domain` (сущности), `repo`, `service`, `web` (контроллеры и DTO). Бизнес-логика живет только в сервисах. Контроллеры тонкие, чтобы потом поверх тех же сервисов можно было добавить REST API (`/api/v1/...`), не трогая логику.

### 3.2. События

Модули общаются через события Spring (`ApplicationEventPublisher`): `FirmwarePublished`, `QuestionCreated`, `EditProposed`, `ArtifactUpdated`, `ArtifactStale`, `SkuLifecycleChanged`. Модуль `task` слушает события и создает задачи. Модуль, который публикует событие, ничего не знает о задачах. Так новые триггеры добавляются без правки старого кода.

### 3.3. Запуск

- Локально: `./mvnw spring-boot:run`, затем браузер на `http://localhost:8080`.
- Данные локально лежат в `./data` (база H2, файлы, индекс поиска). Папка `data/` в `.gitignore`.
- В компании: один jar (`java -jar product-hub.jar --spring.profiles.active=prod`) или Docker-образ (этап 7).

## 4. Модель данных

Ниже логическая модель. Точные типы и индексы определяет разработчик. Обязательные поля отмечены (*).

### 4.1. ProductLine (линейка)

- code* (WEP, WOP, WLC, LR, PTP, LTP, NTU, RG...), name*, family* (Wi-Fi, PON, MES, ESR, VoIP, Media), owner (продакт по умолчанию), sortOrder.

### 4.2. Sku

Идентификация:
- model* - артикул, уникальный (WEP-550K).
- modelNormalized - для поиска: без дефисов и пробелов, в верхнем регистре (WEP550K).
- nameRu, nameEn - полное наименование.
- line* (ProductLine), category* (точка доступа внутренняя, точка доступа уличная, контроллер, мост, OLT, ONT...).
- siteSectionRu, siteSubsectionRu, siteSectionEn, siteSubsectionEn - разделы на сайтах.
- siteStatusRu, siteStatusEn - статус доступности на сайтах (Новинка, Распродажа остатков...).
- owner* - ответственный продакт (User).
- chip - чипсет.

Жизненный цикл (поля из реестра ЖЦ):
- lifecycleStatus* - DEVELOPMENT, NEW, PRODUCTION, EOL_ANNOUNCED, EOL.
- gaDate (квартал или дата запуска), eolAnnounceDate, lastOrderDate, lastShipDate, endOfSupportDate.
- successor (Sku), predecessor (вычисляется обратной связью).
- lastReviewDate, nextReviewDate.

Коммерческий блок (временная копия до интеграции с 1С):
- price, currency, priceList (внутренний, международный), availability (в наличии, под заказ, нет), leadTimeDays.
- commercialUpdatedAt*, commercialUpdatedBy, commercialSource (MANUAL, ONEC). Если данные старше 30 дней, в карточке выводится предупреждение.

Прочее:
- markets - теги категории MARKET.
- description (markdown), keyFeatures (список строк).
- photos - ссылки на артефакты типа "Фото".
- contour - разрешение показа SKU во внешнем контуре (по умолчанию INTERNAL).
- completeness - процент заполненности, вычисляется (раздел 5.4).

### 4.3. Характеристики (SpecDefinition, SpecValue)

Характеристики не хардкодятся в Sku, иначе каждая новая линейка потребует миграции.
- SpecDefinition: key*, labelRu*, labelEn*, unit, valueType (TEXT, NUMBER, BOOLEAN, ENUM), enumValues, group (Радио, Порты, Питание, Конструктив, Окружающая среда, Сертификаты), appliesToCategories, sortOrder, editableBy (PRODUCT или SERVICE_CENTER).
- SpecValue: sku*, definition*, value*.
- Шаблон характеристик для категории = набор SpecDefinition с этой категорией. Новый SKU получает пустые поля из шаблона.

### 4.4. Artifact (артефакт, материал)

Единая база артефактов отдела. Материал может быть привязан к одному или нескольким SKU, к линейке или ни к чему (общий артефакт отдела).

- title*, description.
- type* (ArtifactType).
- language* - RU, EN, RU_EN, NONE.
- status* - ACTUAL, OUTDATED, IN_PROGRESS, EOL, DRAFT.
- owner* (User).
- contour* - INTERNAL или EXTERNAL (можно ли показывать партнерам).
- currentVersion - ссылка на ArtifactVersion.
- externalUrl - если файл живет вне HUB (YouTube, сайт, Confluence). Тогда HUB хранит только ссылку.
- lastReviewedAt*, reviewPeriodDays (по умолчанию из типа).
- skus (связь многие-ко-многим со Sku), tags (многие-ко-многим с Tag).
- createdAt, updatedAt, createdBy.

ArtifactVersion: artifact*, versionNo*, fileName*, storedPath*, sizeBytes, mimeType, sha256, uploadedBy*, uploadedAt*, comment. Новая версия становится текущей, старые остаются в истории и доступны для скачивания.

ArtifactType (справочник, начальное заполнение из `seed/document_types_registry.xlsx`): name*, importance (1-5), defaultContour, producer (кто делает), consumer (кто потребляет), reviewPeriodDays (по умолчанию 90), showInSkuCard (да или нет), sortOrder.

Начальный список типов: Даташит, Прошивка + release notes (как ссылка на модуль прошивок), Руководство по эксплуатации или настройке, Презентация продуктовая, Battle card, Сравнение с конкурентами, Кейс (как ссылка на модуль кейсов), Роадмап линейки, Прайс, Сертификат или test report, Промо-материалы, Фото, Видео, FAQ, Гайд по подбору оборудования, Migration guide, Опросник, Карточка продукта, Шаблон, Прочее.

### 4.5. Firmware (прошивка)

- version*, releaseDate*, status* (BETA, RELEASE, WITHDRAWN), releaseNotes (markdown), file (через FileStorage) или externalUrl, skus* (совместимые устройства), isPublic, publishedBy, publishedAt.
- Для каждого SKU карточка показывает последнюю RELEASE-прошивку как "текущую" и список остальных.

### 4.6. CaseStudy (кейс)

- title*, country*, city, industry (сегмент), customerName, customerVisible (можно ли называть заказчика), summary, challenge, solution, results, deploymentSize (сколько точек, абонентов), year, skus*, artifacts (PDF кейса, фото), publicationAllowed (можно ли во внешний контур), owner.

### 4.7. Tag (тег) и TagCategory

- Категории: LINE, MARKET (страна или регион), SEGMENT (ритейл, склад, офис, outdoor, отель, ISP), COMPETITOR (Huawei, Ubiquiti, TP-Link, Ruijie, HPE Aruba, Ruckus...), TOPIC (Wi-Fi 7, XGS-PON, Mesh...).
- Tag: category*, value*, valueEn, aliases (для поиска и автотегирования), active. Пара category + value уникальна.
- Связь с SKU не делается тегом. Для нее есть прямая связь многие-ко-многим (Artifact.skus, Firmware.skus, CaseStudy.skus), так надежнее и быстрее.
- Создавать теги может только PRODUCT или ADMIN. Остальные выбирают из справочника, произвольных меток нет.

### 4.8. Question (вопросы и правки)

- kind* - QUESTION или EDIT_PROPOSAL.
- target* - SKU, артефакт или прошивка (полиморфная ссылка: targetType + targetId).
- author*, text*, createdAt*.
- status* - NEW, IN_PROGRESS, ANSWERED, ACCEPTED, REJECTED, CLOSED.
- answer, answeredBy, answeredAt.
- publishToFaq - отвеченный вопрос попадает в FAQ карточки и в поиск.

### 4.9. Task (задача)

- title*, description, type* (ANSWER_QUESTION, REVIEW_EDIT, CHECK_DATASHEET, CHECK_BATTLECARD, UPDATE_SITE, REVIEW_STALE_ARTIFACT, REVIEW_SKU, TRANSLATE, MANUAL).
- status* - NEW, IN_PROGRESS, REVIEW, DONE (колонки канбана: Новые, В работе, На проверке, Закрыто).
- assignee*, createdBy (пользователь или SYSTEM), dueDate, priority.
- related - полиморфная ссылка на SKU, артефакт, прошивку или вопрос.
- sourceEvent - какое событие создало задачу.
- Защита от дублей: если открытая задача того же типа на тот же объект уже есть, новая не создается.

### 4.10. Аудит и аналитика

- AuditLog: entityType*, entityId*, action* (CREATE, UPDATE, DELETE, STATUS_CHANGE), field, oldValue, newValue, user*, at*. Пишется для SKU, артефактов, прошивок, кейсов, тегов. Показывается как "История изменений" на странице объекта.
- SearchLog: query*, user, resultsCount*, clickedEntity, at*. Нужен для отчета "что ищут и не находят".
- ViewLog: entityType*, entityId*, user, at*. Нужен для отчета "что реально открывают". Пишется асинхронно, не тормозит ответ.

### 4.11. User

- login*, fullName*, email, roles*, active, defaultLines (линейки, которыми владеет продакт).
- В v0 пользователи заводятся сидом и в разделе администрирования. Позже - синхронизация из AD.

## 5. Модули и функции

Каждый модуль описан через то, что видит пользователь, и критерии приемки.

### 5.1. Общий каркас

- Шапка: логотип текстом "Product HUB", глобальная строка поиска (работает с этапа 5, до этого скрыта), меню (Каталог, Артефакты, Прошивки, Кейсы, Задачи, Дашборд, Справочники), имя пользователя, переключатель "войти как" (dev).
- В подвале время ответа сервера на эту страницу в мс (замер фильтром, раздел 8).
- Язык интерфейса - русский. Все тексты интерфейса сразу выносятся в `messages_ru.properties`, чтобы потом добавить английский без правки шаблонов.
- Страницы ошибок 403, 404, 500 на русском.

### 5.2. Каталог SKU

- Таблица: артикул (ссылка на карточку), наименование, линейка, категория, статус ЖЦ, владелец, заполненность в %, текущая прошивка, дата последнего ревью.
- Фильтры: семейство, линейка, категория, статус ЖЦ, рынок, владелец, "требует ревью" (nextReviewDate прошла). Фильтры и сортировка работают через HTMX без перезагрузки, состояние фильтров отражается в URL (ссылку можно переслать коллеге).
- Быстрый фильтр по тексту в самом каталоге.
- По умолчанию EOL скрыты, включаются галочкой.
- Критерии: каталог на 300 SKU открывается быстрее 200 мс, фильтр применяется быстрее 150 мс.

### 5.3. Карточка SKU

Порядок блоков на странице:

1. Шапка: артикул, наименование RU и EN, линейка, статус ЖЦ (цветная метка), владелец, дата последнего ревью, процент заполненности, кнопки "Задать вопрос" и "Предложить правку".
2. Ключевые особенности и описание.
3. Характеристики по группам. Пустые поля видит только PRODUCT (с подсказкой "заполнить"), остальным пустые не показываются.
4. Прошивки: текущая RELEASE крупно (версия, дата, ссылка на release notes, скачать), ниже свернутый список прочих.
5. Документация и материалы: все артефакты, связанные с SKU, а также артефакты, связанные с линейкой SKU и помеченные "для всей линейки". Сгруппированы по типу, у каждого язык, статус, дата, владелец, скачать. Фильтр по языку RU/EN одним кликом. Устаревшие (OUTDATED) свернуты и отмечены серым.
6. Сравнения и battle cards (артефакты этих типов), с тегом конкурента.
7. Кейсы: карточки кейсов (страна, отрасль, масштаб).
8. Коммерческий блок: цена, наличие, срок поставки, дата обновления, источник. Предупреждение, если старше 30 дней.
9. Фото и видео.
10. Жизненный цикл: даты GA, EOL, LOD, LSD, EoS, преемник и предшественник со ссылками, migration guide, если есть.
11. Планы по продукту (markdown-поле, только внутренний контур).
12. FAQ и "Вопросы и правки": отвеченные вопросы с publishToFaq, ниже открытые вопросы и форма нового вопроса или правки.
13. История изменений (свернута).

Требования:
- Каждый блок проверяет контур и роль. Помощник `canSee(section, user)` определяется в одном месте. В v0 все пользователи внутренние, но проверка уже работает.
- Карточка собирается минимальным числом запросов (без N+1). Критерий: быстрее 300 мс на SKU с 50 материалами.
- Карточку можно открыть по красивому URL: `/sku/WEP-550K`.
- Каждое открытие пишется в ViewLog.

### 5.4. Заведение и правка SKU

- Создать SKU: форма с идентификацией и ЖЦ, после сохранения - пустые характеристики по шаблону категории.
- Создать SKU копированием существующего: копируются характеристики, теги и описание, материалы не копируются.
- Правка по блокам (HTMX, правка на месте). SERVICE_CENTER может править только группы характеристик с editableBy = SERVICE_CENTER и прошивки.
- Отметка "Ревью проведено": ставит lastReviewDate = сегодня и nextReviewDate = сегодня + 90 дней.
- Заполненность считается так: обязательные поля идентификации и ЖЦ, все характеристики шаблона, хотя бы по одному актуальному даташиту RU и EN, хотя бы одна RELEASE-прошивка (для категорий, где прошивка есть), фото, коммерческий блок не старше 30 дней. Веса задаются в конфигурации.
- Критерий: продакт заводит новый SKU по шаблону меньше чем за 15 минут (без учета загрузки файлов).

### 5.5. База артефактов отдела

Отдельный раздел меню "Артефакты", не привязанный к SKU.

- Список с фильтрами: тип, язык, статус, владелец, SKU, линейка, теги (рынок, сегмент, конкурент, тема), контур, "требует ревью". Сортировка по дате обновления.
- Загрузка: перетаскиванием одного или нескольких файлов. Затем форма метаданных с автоподстановкой из имени файла (раздел 5.11). Ограничение размера 200 МБ на файл (настраивается). Разрешенные расширения: pdf, pptx, docx, xlsx, png, jpg, svg, mp4, zip, md, txt.
- Страница артефакта: метаданные, текущая версия (скачать, предпросмотр для pdf и картинок в браузере), история версий, связанные SKU, история изменений, вопросы и правки.
- Загрузка новой версии: старая уходит в историю, lastReviewedAt обновляется, публикуется событие `ArtifactUpdated`.
- Кнопка "Подтвердить актуальность": обновляет lastReviewedAt без новой версии.
- Дедупликация: при загрузке файла с таким же sha256, как у существующей версии, система предупреждает и показывает, где он уже лежит.
- Массовые действия для PRODUCT: сменить статус, добавить тег, привязать к SKU.

### 5.6. Прошивки

- Список прошивок с фильтром по SKU и линейке. Страница прошивки с release notes.
- Публикация (PRODUCT, SERVICE_CENTER, RND): версия, дата, статус, файл или ссылка, совместимые SKU, release notes.
- При публикации со статусом RELEASE генерируется событие `FirmwarePublished`. Оно создает задачи владельцу каждого затронутого SKU: проверить даташит (CHECK_DATASHEET), проверить battle cards (CHECK_BATTLECARD), обновить сайт (UPDATE_SITE). Одна задача каждого типа на SKU, со ссылкой на прошивку.
- Критерий: после публикации прошивка сразу видна в карточках всех совместимых SKU, а задачи появляются на канбане.

### 5.7. Кейсы

- Список кейсов с фильтрами: страна, отрасль, SKU, год.
- Страница кейса: все поля, связанные SKU, вложения.
- Если customerVisible = false, имя заказчика видят только PRODUCT и HEAD.

### 5.8. Вопросы и правки, FAQ

- Форма в карточке SKU, артефакта или прошивки: тип (вопрос или правка), текст.
- Перед отправкой вопроса система ищет похожие отвеченные вопросы и показывает их ("Возможно, ответ уже есть"). Это и есть принцип "сначала посмотри базу".
- Новый вопрос создает задачу ANSWER_QUESTION владельцу объекта, правка - задачу REVIEW_EDIT.
- Владелец отвечает или принимает либо отклоняет правку прямо из карточки или из задачи. Автор видит ответ в разделе "Мои вопросы".
- Отвеченный вопрос с отметкой "в FAQ" показывается в карточке и находится поиском.

### 5.9. Задачи и канбан

- Доска с четырьмя колонками: Новые, В работе, На проверке, Закрыто. Перетаскивание (SortableJS + HTMX-запрос на смену статуса).
- Фильтры: исполнитель (по умолчанию "мои"), тип, SKU, линейка.
- Ручное создание задачи.
- Триггеры:

| Событие | Задача |
|---|---|
| Прошивка опубликована (RELEASE) | CHECK_DATASHEET, CHECK_BATTLECARD, UPDATE_SITE владельцу каждого затронутого SKU |
| Новый вопрос | ANSWER_QUESTION владельцу объекта |
| Предложена правка | REVIEW_EDIT владельцу объекта |
| Артефакт не ревьюили дольше reviewPeriodDays (ежедневная проверка в 07:00) | REVIEW_STALE_ARTIFACT владельцу артефакта, статус артефакта не меняется автоматически |
| У SKU прошла nextReviewDate (ежедневно) | REVIEW_SKU владельцу SKU |
| Статус SKU сменился на EOL_ANNOUNCED | UPDATE_SITE и проверка наличия migration guide |
| Загружен артефакт RU без пары EN того же типа для того же SKU (или наоборот) | TRANSLATE владельцу артефакта |

- Уведомления в v0: счетчик новых задач в шапке. Email и мессенджеры позже.

### 5.10. Мгновенный поиск

- Одна строка в шапке. Результаты появляются по мере ввода начиная со второго символа, с задержкой ввода 150 мс (HTMX `hx-trigger="keyup changed delay:150ms"`).
- Ищет по SKU (артикул, наименование, характеристики), артефактам (название, описание, теги, имя файла), прошивкам (версия, release notes), кейсам, FAQ.
- Результаты сгруппированы по типу, до 5 в группе, со ссылкой "все результаты".
- Нормализация артикулов: "wep550k", "WEP 550K" и "wep-550k" находят WEP-550K. Точное совпадение артикула всегда первое.
- Устойчивость к опечаткам (fuzzy, расстояние 1 для слов от 4 символов).
- Морфология русского и английского (анализаторы Lucene для RU и EN).
- Поиск по содержимому файлов (pdf, docx, pptx через Apache Tika) - желательно в этапе 5, допустимо перенести в этап 6.
- Каждый запрос пишется в SearchLog, клик по результату тоже.
- Индекс обновляется при сохранении объекта. Есть команда полной переиндексации для ADMIN.
- Критерий: ответ на запрос быстрее 100 мс на 300 SKU и 5000 артефактов.

### 5.11. Импорт

Источники начальных данных лежат в `seed/` (оригиналы не изменять).

1. `seed/lifecycle_registry_wifi.xlsx` - реестр ЖЦ Wi-Fi. Колонки: SKU, Линейка, Чип, Статус ЖЦ, Остатки на складе, Дата запуска (GA), Дата анонса EOL, Last Order Date, Last Ship Date, End of Support, Преемник / замена, Owner, Ссылка Product Hub, Последнее ревью, Следующее ревью. Часть строк пустая, их пропускать. Статусы маппятся: Development -> DEVELOPMENT, New -> NEW, Production -> PRODUCTION, EOL -> EOL. Значение "-" считается пустым.
2. `seed/site_catalog_ru_en.xlsx`, лист "Сайты" - каталог сайтов RU и EN. Строка 1 - заголовки групп, строка 2 - заголовки колонок: Раздел, Подраздел, Модель, Статус доступности (RU) и Section, Subsection, Model, Status (EN), плюс колонки проверки. Отсюда берутся все SKU компании (около 300), их разделы и статусы на сайтах. Линейка определяется по префиксу модели (таблица префиксов в конфигурации).
3. `seed/document_types_registry.xlsx`, лист "Реестр по типам" - справочник типов артефактов: Тип документа, Важность, Внешний или внутренний, Производитель, Потребитель.

Импорт папки с файлами (для базы артефактов):
- ADMIN или PRODUCT указывает папку на сервере (локально - на диске).
- Система сканирует файлы и по имени предлагает метаданные. Примеры соглашений из рабочей папки:
  - `Eltex_vs_Huawei_Indoor_EN.pdf` - тип "Сравнение с конкурентами", конкурент Huawei, сегмент Indoor, язык EN.
  - `WEP-3ax_RU.pptx` - тип "Карточка продукта", SKU WEP-3ax, язык RU.
  - `WB-3P-LR5_EN.pdf` - SKU WB-3P-LR5, язык EN.
  - `*_источники.md` - тип "Прочее", внутренний, привязан к одноименному материалу.
  - Пары pptx + pdf с одинаковым именем - один артефакт: pptx как основной файл, pdf как предпросмотр. Хранятся в одной версии как два файла.
- Правила разбора задаются в конфигурации (регулярные выражения), а не в коде.
- Перед записью показывается предпросмотр в виде таблицы: файл, предложенные тип, SKU, язык, теги, найден ли SKU в базе. Пользователь правит и подтверждает. Есть режим dry-run.
- Повторный импорт той же папки не создает дублей (сверка по sha256).

Общие требования к импорту:
- Каждый импорт - отдельная операция с журналом: сколько создано, обновлено, пропущено, ошибки по строкам.
- Повторный запуск идемпотентен: обновляет существующие записи по артикулу, а не дублирует.

### 5.12. Дашборд

Для PRODUCT по своим линейкам, для HEAD по всем:
- Покрытие: число SKU по статусам ЖЦ, средняя заполненность карточек, список 10 самых незаполненных.
- Устаревание: артефакты с просроченным ревью (число и список), SKU с просроченным ревью.
- RU/EN: сколько материалов есть только на одном языке.
- Вопросы: открытые, среднее время ответа за 30 дней.
- Задачи: распределение по колонкам и по исполнителям, просроченные.
- Спрос: топ-20 запросов поиска за 30 дней, топ-20 запросов без результатов, топ-20 открываемых SKU и артефактов.
- Все цифры кликабельны и ведут на отфильтрованный список.

### 5.13. Справочники и администрирование

## 7. Внешний контур (заготовка)

В v0 внешний контур не реализуется. Но уже с первого этапа:
- у SKU, артефактов, прошивок и кейсов есть признак контура или публикации;

- роль PARTNER объявлена, тест проверяет, что пользователь PARTNER не видит INTERNAL-артефакты, цены и battle cards.

## 8. Нефункциональные требования

### 8.1. Скорость

| Действие | Цель (95-й перцентиль, локально, 300 SKU, 5000 артефактов) |
|---|---|
| Открыть каталог | до 200 мс |
| Применить фильтр каталога | до 150 мс |
| Открыть карточку SKU | до 300 мс |
| Ответ мгновенного поиска | до 100 мс |
| Открыть канбан | до 200 мс |

Как достигаем:
- Индексы БД на всех полях фильтров и внешних ключах.
- Никаких N+1: fetch join или entity graph для карточки, проверка в тестах (счетчик SQL-запросов через Hibernate statistics).
- Кэш (Caffeine) для справочников, тегов, шаблонов характеристик. Сброс при изменении.
- Пагинация списков (50 на страницу) или подгрузка при прокрутке.
- Статика с длинным кэшем и версией в имени, сжатие gzip.
- Файлы отдаются потоком с поддержкой Range и ETag.
- Журналы просмотров и поиска пишутся асинхронно.

Замер:
- Фильтр пишет время ответа каждого запроса в лог и в заголовок `Server-Timing`, в подвале страницы видно время.
- Генератор тестовых данных (профиль `perf`) создает 300 SKU и 5000 артефактов без файлов. С ним проверяются цели из таблицы. Результат замера записывается в STATUS.md.

### 8.2. Безопасность

- CSRF включен, HTMX передает токен в заголовке.
- Проверка расширения и MIME загружаемых файлов, ограничение размера, имена файлов на диске генерируются (UUID), оригинальное имя хранится в БД.
- Экранирование вывода (Thymeleaf по умолчанию). Markdown рендерится с санитайзером.
- В v0 нет секретов в коде. Настройки prod берутся из переменных окружения.
- Логи без персональных данных, кроме логина.

### 8.3. Надежность и данные

- Все изменения схемы только через Flyway. Примененные миграции не редактируются.
- Удаление SKU и артефактов мягкое (флаг deleted), физическое удаление делает только ADMIN.
- Бэкап (этап 7): дамп БД и папки файлов по расписанию, инструкция восстановления.

### 8.4. Качество кода

- Тесты на сервисы (бизнес-правила, права, триггеры задач), на импорт (на реальных файлах из `seed/`), на поиск (нормализация артикулов).
- `./mvnw verify` проходит без ошибок перед закрытием этапа.
- Форматирование единое (Spotless или аналог).

## 9. Этапы разработки
